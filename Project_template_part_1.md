# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут просматривать информацию о системе отопления и обновлять настройки
- Пользователи могут удалённо включать/выключать отопление в своих домах.

**Мониторинг температуры:**

- Система получает данные о температуре с датчиков, установленных в домах. 
- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.

### 2. Анализ архитектуры монолитного приложения

Язык программирования: Java
База данных: PostgreSQL
Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
Взаимодействие: Синхронное, запросы обрабатываются последовательно.
Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям, пользователи не могут подключать новые датчики, нет необходимых интерфейсов.
Развёртывание: Требует остановки всего приложения.

Реализации температурных датчиков нет, хотя и заявлено в описании. Также нет никаких данных о том какой датчик какому пользователю принадлежит

### 3. Определение доменов и границы контекстов

При анализе приложения выделены следующие домены:
- Управление отоплением 
- Управление температурой (не реализовано)
- Аутентификация и авторизация (не реализовано)

### **4. Проблемы монолитного решения**
- Код слишком связан и изменения в одной части будут влиять на другие
- Реализация новых функций будет задерживаться из-за единой кодовой базы. При росте команды, управлять 
  проектом будет сложнее и разделить команду тоже, вряд ли, выйдет
- Синхронные запросы могут привезти к задержкам при большом количестве запросов
- Единая точка отказа - при сбоях станет недоступна вся функциональность разом
- Масштабировать можно только всё приложение целиком, а не проблемную часть
- При обновлении приложения будет недоступна вся функциональность

# Задание 2. Проектирование микросервисной архитектуры

Для реализации необходимых требований было принято решение использовать микросервисную архитектуру и выделить следующие домены:
- Авторизация и аутентификация
- Домен устройство умного дома (для каждого типа умных устройств отдельный поддомен)
  - поддомен управление отоплением
  - поддомен управление температурой
  - поддомен управление освещением
  - ....
- Домен умного дома - информация о домах пользователей и их устройствах
  - поддомен управление домами
  - поддомен управление устройствами
  - поддомен управление сценариями


В качестве разделения на микросервисы принято решение разделить домены следующим образом:
- Микросервис авторизации и аутентификации - предлагается использовать готовое решение Keycloak
- Для каждого типа устройств отдельный микросервис для получения данных датчиков, управления настройками и выполнения команд
- Микросервис управления умным домом - принято решение не делить поддомены на разные сервисы, а сделать единый сервис, где хранятся все данные для быстрого отображения пользователю. Сервис практически не имеет бизнес-логики и служить только фасадом данных
- Микросервис регламентных задач для выполнения сценариев для умных устройств - управляет выполнением настроенных пользователем задач.

Взаимодействие между сервисами осуществляется асинхронными методами с помощью брокера сообщений Kafka.

Основные связи:
- Микросервис умного устройства получает данные с датчиков и отправляет команды на устройство
- Микросервис умного устройства отправляет данные с датчиков в сжатом виде на сервис управления умным домом (например, последннее измерение температуры) для быстрого отображению пользователю. При необходимости отображения основного объема данных, можно обратиться с помощью синхронного запроса в сам микросервис устройства.
- Микросервис управления умным домом отправляет команды для устройства в микросервис умного устройства и заданные сценарии в сервис управления сценариями

В дальнейшем, при росте нагрузки можно масштабировать выбранные сервис умного устройства, которые испытывают максимальные нагрузки и\или сервис умного дома, в случае роста запросов к интерфейсу.
В дальнейшем, можно разделить сервис умного устройства на сервис сбора данных с датчиков, сервис управления настройками и сервис команд, если того потребует рост клиентой базы и увеличение команды разработки.
